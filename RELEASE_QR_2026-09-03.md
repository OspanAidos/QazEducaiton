# QazEducation — QR-оплата и автоматическая подача, 03.09.2026

> Для создания новых QR этот документ заменён релизом
> `RELEASE_CATALOG_QR_2026-09-04.md`: организация требует товары каталога,
> а доплата 7 000 ₸ временно заблокирована до появления отдельной позиции.

Этот документ описывает обновление оплаты поверх архива
`QazEducation-production-30-scholarships-2026-08-27.zip`.
Он имеет приоритет над прежними инструкциями по оплате в этом проекте.
Действующий сайт, Supabase, ключи и кабинет ApiPay при подготовке архива НЕ изменялись.

## Согласованные правила

| Пакет | Новый платёж | Результат |
| --- | ---: | --- |
| Подбор вуза | 3 000 ₸ | Только подбор вуза; заявка в конкурс не подаётся |
| Участие в конкурсе + подбор вуза | 10 000 ₸ | Доступ к подбору и автоматическая подача заполненной заявки |
| Участие после оплаченного подбора вуза | 7 000 ₸ | Существующие 3 000 ₸ учитываются; открывается полный пакет |

Название услуги — «Подбор вуза». Каталог ApiPay не используется.
Число стипендий остаётся 30. Сертификаты и импорт старых заявок в этом обновлении
не перерабатывались; прежние файлы импорта сохранены, но не выполнялись.

## Как работает оплата

- `/payment` и `/match` используют общую форму Kaspi QR. Форма не выставляет
  счета по номеру телефона и не предлагает загрузку чека для подтверждения.
- Сервер сам определяет сумму и владельца заказа. Сумма, статус и пользователь
  из тела браузерного запроса не используются для подтверждения платежа.
- До создания конкурсного QR сервер проверяет анкету, возраст, документы,
  гражданство, поддержку и согласия. Необходимо завершить обязательные поля.
- Подтверждение принимается по проверенному уведомлению ApiPay и повторной
  сверке объекта счёта через серверный API. Проверяются подпись, ID, владелец
  внешнего заказа, сумма, валюта при наличии и рабочий режим.
- После оплаты база повторно проверяет заявку и подаёт её автоматически.
  Для этого не требуется держать вкладку открытой. При нехватке данных либо
  закрытии приёма платёж остаётся записанным, а заявка не подаётся вслепую.
  Участник видит причину и возможность завершить заполнение/обратиться в поддержку.
- В интерфейсе есть кнопка «Обновить страницу» и переход к заявке/подбору.
- Заявка на доработке не отправляется повторно из-за запоздалого уведомления.
  Участник завершает исправления прежней кнопкой повторной подачи, без новой оплаты.
- При создании QR конкурсная заявка переходит в «Ожидают оплату».
- Истечение таймера означает окончание окна сканирования, не подтверждение отмены.
  Новый QR не создаётся до разрешения предыдущей попытки платёжной системой.
- При неоднозначной ошибке создания повторный POST не отправляется: сервер
  ищет тот же счёт по `external_order_id`. Если найти его не удаётся, попытка
  остаётся на сверке; автоматически отпускать её или ставить «Оплачено» нельзя.
- Повторные уведомления не создают повторную заявку. Опрос состояния на странице
  помогает восстановить пропущенное уведомление при возвращении участника.
  Отдельный фоновый планировщик сверки в этом релизе не добавлялся.
- Денежные возвраты, кнопки возврата и обращения к API возврата НЕ реализованы.
  Фактически пришедшие от провайдера сведения о возврате сохраняются и требуют
  сверки, чтобы не показывать ошибочный оплаченный доступ. Заявки не удаляются.
  Существующие юридические тексты не переписывались этим техническим обновлением.

## Что проверено локально

- 29 автоматизированных тестов: подпись и поля счёта, суммы и доплата, неподанные
  заявки без оплаты, автоматическая подача, повторные события, запоздалая оплата,
  сканирование без оплаты, ошибки сети, права обычного пользователя, доработка,
  проверки документов/возраста/согласий, учёт фактических возвратов, повторная миграция.
- SQL проверен в отдельной временной PostgreSQL-совместимой базе PGlite 0.5.8
  на синтетических данных. Тесты используют реальные функции миграции, старый
  административный переход и триггеры подачи/очереди уведомлений проекта.
- Обработчики Edge Functions проверены с подменёнными Supabase и ApiPay;
  никаких обращений к боевой базе или денежных операций тесты не делают.
- Сборка Vite успешно проходит. Зависимости приложения и пакетный lock-файл
  не заменялись. Для тестов имеется отдельный `tests/package-lock.json`.

Не проверены: реальная транзакция Kaspi, развёртывание Edge Functions, фактические
настройки/RLS работающего проекта Supabase, доставка Telegram на живом аккаунте,
реальное конкурентное выполнение транзакций на многосессионном PostgreSQL,
визуальное отображение в браузере. Эти проверки не следует считать выполненными.

Локальный повтор тестов после `npm ci` в корне:

## Настройки и сборка на Mac

В исходном архиве отсутствовали значения публичного подключения Supabase.
Вложенная `dist` — проверочная сборка без подключения к базе; НЕ загружайте её
на действующий сайт как есть. Вход и оплата в ней не настроены.

Используйте ваш существующий `.env.local` рядом с `package.json`, не внутри `dist`:

```text
VITE_SUPABASE_URL=<URL вашего проекта Supabase>
VITE_SUPABASE_PUBLISHABLE_KEY=<публичный publishable или anon ключ этого проекта>
```

Секретные ключи туда не добавляются. Для проверки исходников: `npm ci`, затем
`npm run dev`. После настройки выполните `npm run build` и проверяйте именно
эту новую `dist`. `npm run preview` не подставляет настройки в старую сборку.

## Обновление работающего сайта — выполнять только после согласования публикации

Ни один из перечисленных ниже шагов не был выполнен при подготовке архива.

1. Сохранить резервную копию базы и действующей версии сайта/Edge Functions.
   Убедиться, что использован тот же проект Supabase, что и на работающем сайте.
2. В согласованное окно обслуживания приостановить новые оплаты. Для новой
   `apipay-invoice` отсутствие `APIPAY_PAYMENTS_ENABLED=true` означает запрет
   создавать счета. Старый обработчик этого флага не знает: для остановки старого
   приёма нужно сначала опубликовать новый `apipay-invoice` с флагом `false`.
   До SQL он может возвращать временную ошибку проверки — в это время платежи
   не проверять вручную и не подтверждать поддельными данными.
3. Если миграции исходного проекта от 27.08 ещё не применены, сначала завершить
   их установку по старой инструкции. Для уже актуальной базы выполнить только
   `supabase/qr-payments-v2.sql` целиком в SQL Editor. Скрипт содержит транзакцию,
   расширяет таблицу платежей, заменяет функции подачи/подтверждения и ограничивает
   клиентское изменение статусов. Существующие записи не удаляет и не импортирует.
   Старые миграции после него повторно не запускать: они переопределяют защиту.
4. Опубликовать обе обновлённые функции `apipay-invoice` и `apipay-webhook` вместе
   с их импортами `supabase/functions/_shared/apipay-core.js` и `apipay-runtime.ts`.
   При CLI-развёртывании относительные импорты включаются в сборку функций.
   Не копировать только один `index.ts` в редактор без общих файлов.
   Для webhook сохраняется `verify_jwt=false`, подпись проверяет сам обработчик.
   Для invoice сохраняется `verify_jwt=true`, а пользователь дополнительно
   проверяется через Supabase Auth. Эти настройки уже есть в `supabase/config.toml`.
5. Сохранить существующие серверные `APIPAY_API_KEY`, `APIPAY_WEBHOOK_SECRET` и
   штатные секреты Supabase. Не публиковать их в браузере, архиве или Git.
   Хост API в новом коде фиксирован; `APIPAY_BASE_URL` больше не используется.
   Секрет подписи должен соответствовать ключу **QazEducation Production**, а
   адрес уведомлений — его функции `/functions/v1/apipay-webhook`.
   Старый API-ключ другого сайта не удалять/не перенастраивать этим обновлением.
6. Собрать frontend с вашими публичными настройками Supabase и опубликовать
   содержимое новой `dist` с резервной копией старой версии. SQL, тесты, исходники,
   `.env.local` и секреты не помещать в публичную папку сайта.
7. Сначала оставить `APIPAY_PAYMENTS_ENABLED=false` и проверить вход, чтение
   истории, права ролей и доставку тестового уведомления ApiPay. HTTP 200 на
   `webhook.test` подтверждает только доставку/проверку подписи, не оплату.
8. Только после отдельного разрешения на денежную проверку установить
   `APIPAY_PAYMENTS_ENABLED=true` и `APIPAY_CHECKOUT_USER_IDS=<UUID тестирующего
   участника Supabase Auth>` — без угловых скобок. Можно перечислить несколько
   UUID через запятую. Остальные участники не смогут создавать новые счета.
   Выполнить одну заранее согласованную реальную оплату соответствующего пакета.
   Не менять сумму на 1 ₸, не симулировать `paid` в рабочей базе и не переключать
   действующую организацию в песочницу ради теста. Возврат денег этим релизом
   не выполняется; это нужно учесть до разрешения реальной проверки.
9. Сверить один и тот же ID счёта и сумму в ApiPay и Supabase, статус оплаты,
   подачу корректной заявки, однократность события и доступ к подбору. Если платёж
   уже списан, но подтверждения нет, не платить второй раз — открыть журналы.
10. Только после успешной проверки и разрешения общего запуска убрать
    `APIPAY_CHECKOUT_USER_IDS`, сохранив `APIPAY_PAYMENTS_ENABLED=true`.
    Пустой/отсутствующий список означает доступ для всех авторизованных участников.

## Совместимость и восстановление

- Нельзя заменять только frontend: для доплаты и новой проверки требуется SQL
  и обе новые функции. После применения SQL старый `apply_apipay_payment_event`
  намеренно недоступен серверной роли; старый webhook до обновления будет получать
  ошибку. Поэтому требуется короткое согласованное окно и быстрая публикация
  нового webhook. После обновления проверить отложенные доставки и счета.
- Доступ по уже существующим подтверждённым платежам сохраняется. Массовая
  сверка старых платежей с ApiPay не выполнялась. Перед запуском отдельно
  проверить, что среди старых подтверждённых записей нет тестовых/ручных платежей.
- Редкие фактические двойные списания должны быть видны в истории. Поэтому старое
  ограничение «одна оплаченная запись на тип» заменено обычным индексом; новые
  попытки защищены серверным резервированием с блокировкой пользователя.
- При проблемах сначала поставить `APIPAY_PAYMENTS_ENABLED=false`. Не удалять
  оплаты/события, не сбрасывать `pending` и не откатывать базу вслепую.
  Старый код не понимает 7 000 + 3 000 ₸; возврат к нему после таких платежей
  потребует совместимой версии, а не простой замены `dist`.
- Неопределённая попытка создания без найденного счёта требует ручной сверки
  ответственным специалистом с ApiPay. Нельзя разрешать повторное списание лишь
  по таймеру или нажатию «Я оплатил».
- Заявка продолжает использовать существующую очередь Telegram-уведомлений.
  Новый планировщик/механизм отправки Telegram и генерация сертификатов в этом
  изменении не добавлены.

Технический контракт сверялся с официальной документацией ApiPay:
[QR и уведомления](https://apipay.kz/docs.html),
[проверка подписи и повторные доставки](https://apipay.kz/for-ai).
